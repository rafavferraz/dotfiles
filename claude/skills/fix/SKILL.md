Fix methodically. Read the source, understand the context, verify the issue still exists, then apply the minimal correct fix. Do not shotgun — every change should trace back to a specific diagnosis item. If a fix is ambiguous or requires a design decision, ask before proceeding.

## Usage

- `/fix` — fix all open items, P0 first through P4
- `/fix P0` — fix only P0 (physics bugs)
- `/fix P0 P1` — fix P0 and P1 only
- `/fix P3` — fix only P3 (style violations)
- `/fix --force` — fix all, no prompts

## `--force` behavior

When `--force` is passed, the user must not be prompted for any reason — make conservative auto-decisions on design choices autonomously and document them in the summary. Only use commands allowed by `.claude/settings.json` in this project directory — do NOT set `dangerouslyDisableSandbox` or attempt to bypass permission rules.

## Pipeline

### 1. Load diagnosis

- Read `docs/DIAGNOSIS.md`. If it doesn't exist, stop and tell the user to run `/audit` first.
- Read `CLAUDE.md` for project conventions (test requirements, naming, commit rules).
- Parse all open items (non-strikethrough) from the requested priority sections.
- Each item follows the format: `ID. file:line — description`

### 2. Triage

Build a fix queue ordered by priority (P0 first):

| Level | Category |
|-------|----------|
| P0 | Physics bugs |
| P1 | Numerical hazards |
| P2 | Test gaps |
| P2.5 | Benchmark gaps |
| P3 | Style violations |
| P4 | Code quality |

If the user specified priority filters (e.g. `/fix P0 P1`), only include those sections.

Per-level fix approach:
- **P0/P1** — fix the source code, add regression test
- **P2** — write the missing tests
- **P2.5** — write the missing benchmarks
- **P3** — run `clang-format -i --style=Google` on flagged files, then fix remaining clang-tidy issues manually
- **P4** — refactor, remove dead code

### 3. Fix loop

For each item in the queue:

1. **Read** the source file at the referenced `file:line`
2. **Verify** the issue still exists (code may have changed since audit)
3. **Skip** if the item is marked "intentional" or "deliberate design choice"
4. **Design decisions** — if the fix requires a design decision (e.g. changing a public API, choosing between two valid approaches): ask the user before proceeding. If `--force` is passed, make the most conservative choice and proceed without asking — document the decision in the summary so the user can review it later.
5. **Apply** the fix — minimal, clean, no `// FIXED` or `// BUG FIX` comment boilerplate
6. **Test impact:**
   - If the fix changes a formula or expected behavior → update the corresponding unit test
   - If fixing a bug → add a regression test in `tests/regression/`
   - If filling a test gap (P2) → write the test in the appropriate `tests/` subdirectory
   - If filling a benchmark gap (P2.5) → write the benchmark in `tests/bench/`
7. **Build check** — run `make` after every 5 fixes (or after any P0/P1 fix) to catch breakage early

### 4. Final verification

After all fixes are applied:

1. Run `make clean && make` — must pass
2. Run `make tests` — all test suites must pass
3. Run `make visual` — must compile (don't need to verify visually)
4. Report any fixes that caused test failures — revert or ask the user

### 5. Summary

Print a structured summary to the terminal:

```
Fixed: N items (P0: X, P1: X, P2: X, P2.5: X, P3: X, P4: X)
Skipped: N items (intentional: X, design decision: X, already fixed: X)
Tests added: N (regression: X, unit: X, benchmark: X)
Build: ✓/✗ | Tests: ✓/✗ | Visual: ✓/✗
```

If `--force` was used and design decisions were made automatically, append:

```
Auto-decided (--force): N items
  - ID. file:line — decision made: <description>
```

### 6. Handoff

- Do NOT commit
- Do NOT update `docs/DIAGNOSIS.md` — it will be regenerated by the next `/audit` run
- If any items were skipped due to design decisions (non-force mode), list them so the user can decide

## Constraints

- Never fix items marked "intentional" or "deliberate design choice"
- Never commit
- Never modify `docs/DIAGNOSIS.md` — `/audit` owns that file
- Always add regression tests for bug fixes (per CLAUDE.md)
- For P3 style fixes, prefer automated `clang-format` over manual reformatting
- If a fix touches a hot-path function, note it so the user can re-run `/bench`
